# คู่มือการวางแผน Sprint และการจัดการงาน

## ภาพรวม

คู่มือนี้จัดทำขึ้นเพื่อกำหนดกรอบการทำงานมาตรฐานสำหรับการวางแผน Sprint การจัดการ Task และการจัดสรรเวลา เพื่อให้เกิดความโปร่งใส มีความรับผิดชอบ และพัฒนาอย่างต่อเนื่องในทุกทีม

### ปัญหาที่พบใน Q4 (ที่นำไปสู่การเปลี่ยนแปลง)

1. **งานแทรกตลอดเวลา** - แก้ปัญหาเฉพาะหน้าจนคุมเวลาไม่ได้
2. **Technical Debt สะสม** - ระบบยิ่งนานยิ่งแก้ยากและช้าลง
3. **ทีมเหนื่อยล้า (Burnout)** - แก้งานดึก ส่งผลต่อสุขภาพและไม่มีเวลาพัฒนาทักษะ

### เป้าหมายของ Planning Driven Strategy

🎯 **Transform Workflow** - เปลี่ยนจากการ "รับงานแทรก" มาเป็น "ทำงานตามแผน"  
🎯 **Empower People** - มีเวลาในการเรียนรู้ทักษะใหม่ (Upskill) และพัฒนาตัวเอง

## 1. โครงสร้างการแบ่งเวลาใน Sprint

### โมเดล 6-2-1-1 (Sprint 10 วันทำการ)

เราแบ่งสัดส่วนงานใน Sprint ออกเป็น 4 ประเภทหลัก เพื่อให้ทีมมีเวลาทั้งการส่งมอบงานและการพัฒนาตัวเอง:

| **ประเภทงาน** | **จำนวนวัน** | **คำสำคัญในการจัดหมวดงาน (Trigger Keywords)** | **ผลลัพธ์ที่คาดหวัง** |
|---------------|--------------|-----------------------------------------------|---------------------|
| **Partner Work** | 6 วัน | • "ลูกค้าต้องการ..."<br>• "Partner สั่งให้..."<br>• "Feature ตาม Requirement"<br>• "Bug ที่ลูกค้ารายงาน"<br>• "ตาม Roadmap ที่วางไว้"<br>• "Ticket จาก Partner" | Features / Bug Fixes |
| **Technical Debt** | 2 วัน | • "Code ตรงนี้ซ้ำซ้อน ควรจะ Refactor"<br>• "ระบบช้า ควร Optimize"<br>• "Library เวอร์ชันเก่า ควร Upgrade"<br>• "Test Coverage ต่ำ ควรเพิ่ม Unit Test"<br>• "แก้งานชั่วคราวไว้ ควรกลับมาแก้ให้ถูกต้อง"<br>• "ลบ Dead Code" | ลดหนี้ทางเทคนิค |
| **Product Improvement** | 1 วัน | • "ถ้ามี Tool นี้จะทำงานได้เร็วขึ้น"<br>• "R&D เครื่องมือใหม่"<br>• "เพิ่ม Feature ที่ทีมเห็นว่าควรมี"<br>• "สร้าง Script อัตโนมัติ"<br>• "ระบบ Monitoring/Alert"<br>• "งานนี้ถ้าทำน่าจะออกมาดีนะ" (แต่ลูกค้าไม่ได้สั่ง) | POC / Internal Tools |
| **Self Improvement** | 1 วัน | • "อยากเรียนรู้ Framework ใหม่"<br>• "ไปดูเรื่อง...มาให้หน่อย"<br>• "ทดลองใช้ Technology ใหม่"<br>• "เตรียม Knowledge Sharing"<br>• "อ่าน Documentation เพื่อเพิ่มทักษะ" | Knowledge Sharing Session |

**เคล็ดลับในการแยกหมวด**: ถามตัวเองว่า "ใครเป็นคนขอ?" 
- **ลูกค้า/Partner ขอ** → Partner Work
- **ระบบมีปัญหา/ควรแก้** → Technical Debt  
- **ทีมอยากสร้างเพื่อช่วยงาน** → Product Improvement
- **ตัวเองอยากเรียนรู้** → Self Improvement

### ตัวอย่างการจัดหมวดงาน

| งานที่เข้ามา | หมวดที่ถูกต้อง | เหตุผล |
|-------------|---------------|--------|
| "Partner ต้องการให้เพิ่ม Login ด้วย Google" | Partner Work | ลูกค้าสั่งโดยตรง |
| "ระบบ Login ช้า ควร Cache Session" | Technical Debt | แก้ไขประสิทธิภาพระบบเดิม |
| "สร้าง Dashboard แสดง Metrics สำหรับทีม" | Product Improvement | ทีมเห็นว่าควรมี แต่ลูกค้าไม่ได้ขอ |
| "เรียนรู้ Redis เพื่อนำมาใช้งาน" | Self Improvement | พัฒนาทักษะส่วนตัว |
| "เพิ่ม LGTM Bot สำหรับ Code Review" | Product Improvement | Internal Tool ที่ช่วยทีม |
| "แก้ Bug การคำนวณที่ลูกค้ารายงาน" | Partner Work | งานจากลูกค้า |
| "Refactor API เก่าให้เป็น RESTful" | Technical Debt | ปรับปรุงโค้ดเดิม |

### การปรับสัดส่วนตามบริบท

สัดส่วน 6-2-1-1 เป็น **แนวทางมาตรฐาน** แต่สามารถปรับได้ตามสถานการณ์:

| สถานการณ์ | สัดส่วนที่แนะนำ | เหตุผล |
|----------|----------------|--------|
| Sprint ปกติ | 6-2-1-1 | สมดุลทุกด้าน |
| มีแผนงานแน่นกับลูกค้า | 8-1-0.5-0.5 | เน้น Delivery (เหมือนทีม F8) |
| ต้องแก้ Tech Debt เร่งด่วน | 5-3-1-1 | เพิ่มเวลาแก้หนี้เทคนิค |
| Sprint มีวันหยุด 2 วัน | 5-2-0.5-0.5 | ลดตามสัดส่วน รักษา Tech Debt |

**หลักการสำคัญ**: ไม่ว่าจะปรับสัดส่วนแบบไหน ต้องรักษาเวลาสำหรับ **Tech Debt + Improvement อย่างน้อย 2-3 วัน** เสมอ

## 2. มาตรฐานการจัดการ Task

### กฎทอง: "ทุกอย่างต้องเป็น Task"

เพื่อให้มั่นใจในการมองเห็นงานและติดตาม Burndown ได้อย่างแม่นยำ งานทั้งหมดต้องปฏิบัติตามมาตรฐานเหล่านี้:

### 2.1 การลงทะเบียน Task

✅ **บังคับ**: ทุกงานต้องมีตั๋ว (Ticket) ในระบบ ไม่ว่าจะเป็นหมวดใด  
✅ **ไม่มีข้อยกเว้น**: แม้แต่งานแก้ไขฉุกเฉินก็ต้องมี Task  
❌ **ห้าม**: รับงานปากเปล่าหรือทำงานที่ไม่มี Ticket

### 2.2 การประเมิน Story Points

Story Points วัด**ความซับซ้อนและความพยายาม** ไม่ใช่แค่เวลาที่ใช้

#### Story Points Estimation Guide

| **Story Points** | **ความรู้เกี่ยวกับงาน** | **Dependencies** | **ความพยายามในการทำ** |
|-----------------|------------------------|------------------|----------------------|
| **1** | รู้ทุกอย่าง (Everything) | ไม่มี (None) | น้อยกว่า 2 ชม. |
| **2** | รู้เกือบทั้งหมด (Almost everything) | เกือบไม่มี (Almost none) | ครึ่งวัน |
| **3** | รู้บางอย่าง (Something) | มีบ้าง (Some) | 1-2 วัน |
| **5** | รู้เกือบไม่มี (Almost nothing) | มีไม่มาก (Few) | 2-3 วัน |
| **8** | ไม่รู้เลย (Nothing) | มากกว่าเล็กน้อย (More than few) | ประมาณ 1 สัปดาห์ |
| **13** | ไม่รู้เลย (Nothing) | ไม่แน่ใจ (Unknown) | มากกว่า 1 สัปดาห์ |


**คำแนะนำ**: 
- งานที่ได้ **8 หรือ 13 Points** ควรแบ่งย่อยเป็น Task เล็กๆ (Break Down)
- ถ้าไม่แน่ใจ ให้เลือกตัวเลขที่สูงกว่า (Better Safe Than Sorry)
- ใช้ Planning Poker เพื่อให้ทีมประเมินร่วมกัน

#### ตัวอย่างการให้ Point

| งาน | Points | เหตุผล |
|-----|--------|--------|
| แก้ไขสี Button | 1 | รู้วิธีทำชัดเจน ไม่มี Dependency |
| เพิ่มฟิลด์ใน Form + บันทึก Database | 2 | เคยทำแล้ว รู้ขั้นตอน |
| สร้าง API ใหม่ + เชื่อม Frontend | 3 | รู้โครงสร้าง แต่ต้องประสานหลายส่วน |
| ทำระบบ Authentication ด้วย OAuth | 5 | เคยอ่านแต่ยังไม่เคยทำ มี Dependency กับระบบภายนอก |
| Migrate Database ขนาดใหญ่ | 8 | ซับซ้อน มีความเสี่ยง ต้องวางแผนดี |
| สร้างระบบ Recommendation Engine | 13 | ไม่เคยทำ ไม่แน่ใจขั้นตอน → **ควรแบ่งย่อย** |

### 2.3 Definition of Done (DoD)

แต่ละประเภทงานมีเกณฑ์การเสร็จสมบูรณ์ที่แตกต่างกัน:

| ประเภท | Definition of Done |
|--------|-------------------|
| **Partner Work** | ✅ โค้ดถูก Merge<br>✅ ผ่านการทดสอบ (Testing)<br>✅ Deploy ขึ้น Production<br>✅ Partner ยืนยันว่าใช้งานได้ |
| **Technical Debt** | ✅ การปรับปรุงได้รับการตรวจสอบแล้ว<br>✅ Test Coverage เพิ่มขึ้น (ถ้ามี)<br>✅ เอกสารอัปเดตเรียบร้อย<br>✅ ไม่มี Regression Bug |
| **Product Improvement** | ✅ POC/Tool สามารถใช้งานได้<br>✅ ผลลัพธ์ได้รับการจัดทำเป็นเอกสาร<br>✅ **มีการแชร์ผลการค้นพบกับทีม** |
| **Self Improvement** | ✅ มีการจัด Knowledge Sharing Session<br>✅ **หรือ** เอกสารสรุปถูกเผยแพร่แล้ว<br>✅ ทีมสามารถนำไปใช้ได้จริง |

**สำคัญมาก**: งาน **Improvement และ Product** จะถือว่าเสร็จสมบูรณ์ก็ต่อเมื่อ **มีการแชร์ความรู้กับทีมแล้วเท่านั้น** การทำเสร็จแต่ไม่แชร์ = ยังไม่จบ

### การจัดการ Story Points สำหรับงาน Improvement

**คำถาม**: Improvement ควรใส่ Point หรือไม่?

**คำตอบ**: ✅ **ควรใส่** เพื่อความโปร่งใสและวัดผลได้

**วิธีจัดการ Burndown Chart**:

```
Option 1 (แนะนำ): นับ Improvement เป็น Committed Work
→ Burndown แสดงภาพรวมจริงของงานทั้งหมด

Option 2: แยก Chart สำหรับ Improvement
→ Track แยกต่างหาก ไม่รบกวน Partner Work Chart

Option 3: ใช้ Cumulative Flow Diagram
→ เห็นการไหลของงานทุกประเภทพร้อมกัน
```

## 3. การรับมือกับปัญหาและความยืดหยุ่น

### 3.1 Gatekeeper Rule - ป้องกันงานแทรก

**หลักการ**: เฉพาะ **Lead/PM เท่านั้น** มีสิทธิ์อนุมัติงานแทรก

#### กฎการป้องกันงานแทรก

| สถานการณ์ | การจัดการ |
|----------|----------|
| ❌ พนักงานรับงานแทรกโดยตรงจากฝ่ายอื่น | **ห้าม** - ต้องให้ฝ่ายนั้นติดต่อ PM |
| ✅ งานด่วนผ่าน PM | ประเมิน Severity ก่อน ตาม SLA |
| ✅ งานทุกชิ้น | ต้องมี Ticket และผ่าน Approve |
| 💬 การสื่อสาร | ต้องผ่าน PM ไปยังทีมเท่านั้น |

### 3.2 Severity Logic (SLA) - ตัดสินใจว่าจะแทรกหรือไม่

เมื่อมีงานด่วนเข้ามา ใช้ตารางนี้ในการตัดสินใจ:

| **Severity** | **บริบท (Context)** | **แนวทางการจัดการ (Action Plan)** |
|-------------|--------------------|---------------------------------|
| **🔴 1: Critical** | • ระบบล่ม<br>• วิกฤต<br>• Payment พัง<br>• ผู้ใช้ไม่สามารถเข้าระบบได้ทั้งหมด | **Stop Everything**<br>แทรกงานได้ทันที แก้ให้จบ |
| **🟠 2: High** | • ฟีเจอร์หลักพัง<br>• แต่ระบบยังใช้งานได้<br>• ผลกระทบเฉพาะกลุ่ม | **Lead Decision**<br>อาจแทรก หรือรอ Patch Sprint ถัดไป |
| **🟡 3: Medium/Low** | • ข้อมูลผิด<br>• คำผิด<br>• สีไม่ตรง<br>• ฟีเจอร์ใหม่<br>• Nice to have | **No Insertion**<br>ลง Backlog เท่านั้น **ห้ามแทรก** |

#### ตัวอย่างการใช้ Severity Logic

| งานที่เข้ามา | Severity | การจัดการ |
|-------------|----------|----------|
| "ระบบ Login ล่ม ไม่มีใครเข้าได้" | 🔴 Critical | แทรกทันที |
| "ระบบคำนวณผิด แต่ยังใช้งานได้" | 🟠 High | Lead ตัดสินใจ |
| "ต้องการเปลี่ยนสีปุ่ม" | 🟡 Low | ลง Backlog ห้ามแทรก |
| "Payment Gateway ล่ม" | 🔴 Critical | แทรกทันที |
| "Export Excel ไม่ได้" | 🟠 High | ประเมินผลกระทบก่อน |

### 3.3 สิ่งที่เราจะ "ไม่ทำ" (NOT-TO-DO List)

เพื่อปกป้อง Sprint Planning เราต้องมีวินัยในการปฏิเสธสิ่งเหล่านี้:

| สิ่งที่ไม่ทำ | คำอธิบาย | ข้อยกเว้น |
|------------|---------|-----------|
| 🚫 **No Ticket, No Work** | ไม่รับงานปากเปล่า<br>ทุกงานต้องลง ClickUp/Jira | ไม่มี |
| 🚫 **No Direct Orders** | ไม่รับงานแทรกระหว่าง Sprint | ยกเว้นฉุกเฉินระดับ 1 (Critical) |
| 🚫 **Protect the 6-2-1-1** | ไม่เบียดเบียนเวลา Tech Debt และ Upskill | ถ้าจำเป็นต้องลด ให้ลด Partner ก่อน |

### 3.4 วิธีจัดการเมื่อมีงานฉุกเฉิน

เมื่อมีงาน Critical เข้ามาระหว่าง Sprint:

**ขั้นตอนการจัดการ**:

1. **ประเมิน Severity** ตามตาราง SLA
2. **หาเวลาชดเชย**:
   - ดึงจาก Improvement/Product (วันที่ 8-9) ก่อน
   - ถ้าไม่พอ ขยาย Sprint หรือลด Scope ของ Partner Work
3. **บันทึกใน Retro**:
   - งานอะไรถูกตัด
   - เวลาที่ใช้ไป
   - วิธีป้องกันในอนาคต
4. **วางแผนชดเชย**: นำงานที่ตัดไปใส่ใน Sprint ถัดไป

**ตัวอย่าง**:
```
Sprint เดิม: 6 Partner + 2 Tech Debt + 1 Product + 1 Improvement
งาน Critical เข้ามา: ใช้เวลา 1.5 วัน

ปรับเป็น: 
- 6 Partner (คงเดิม)
- 2 Tech Debt (คงเดิม - ต้องรักษา)
- 0.5 Product (ลดลง)
- 0 Improvement (ตัดออก → ย้ายไป Sprint ถัดไป)
- 1.5 Emergency (งานฉุกเฉิน)
```

### 3.5 การจัดการเมื่อ Sprint มีวันหยุด

**หลักการ**: ปรับสัดส่วนตามลำดับความสำคัญ

**Priority Order**: Partner Work > Technical Debt > Product Improvement > Self Improvement

**ตัวอย่าง Sprint 10 วัน → เหลือ 8 วัน (หยุด 2 วัน)**:

| แบบปกติ (10 วัน) | ปรับใหม่ (8 วัน) | หมายเหตุ |
|-----------------|----------------|---------|
| Partner: 6 วัน | Partner: 5 วัน | ลด 1 วัน (ต้องสื่อสารกับ Partner) |
| Tech Debt: 2 วัน | Tech Debt: 2 วัน | **คงไว้** (สำคัญต่อระบบ) |
| Product: 1 วัน | Product: 0.5 วัน | ลดครึ่ง |
| Improvement: 1 วัน | Improvement: 0.5 วัน | ลดครึ่ง |

### 3.6 การจัดการวันสุดท้ายของ Sprint (Ceremony Day)

**ปัญหา**: วาง Improvement ไว้วันสุดท้าย แต่ Retro + Demo ใช้เวลาครึ่งวันไป

**แนวทางแก้ไข**:

```
❌ หลีกเลี่ยงแบบนี้:
วันที่ 9: งานปกติ
วันที่ 10: Improvement + Demo + Retro + Planning (วุ่นวาย)

✅ ทำแบบนี้แทน:
วันที่ 1-7:   Partner Work + Tech Debt
วันที่ 8-9:   Improvement + Product + Knowledge Sharing
วันที่ 10:    Demo + Retro + Planning (Ceremony Day โฟกัสเดียว)
```

**การจัดการ Refine และ Ceremony**:

| กิจกรรม | หมวดที่นับ | เวลาที่แนะนำ |
|---------|-----------|-------------|
| **Refine** | Partner Work | ครึ่งวัน (ไม่ควรเกิน) |
| **Demo** | Ceremony Day | 30-45 นาที |
| **Retro** | Ceremony Day | 30-45 นาที |
| **Planning** | Ceremony Day | 1-2 ชั่วโมง |

**คำเตือน**: ถ้า Refine ใช้เวลา 1 วันเต็ม แสดงว่า Task breakdown ไม่ดีพอ ควรทำ Continuous Refinement แทน
